01 · Overview

One kitchen, four order channels, zero lost tickets

The platform is a client-authoritative, offline-first modular monolith partitioned into DDD bounded contexts. Four order channels — counter POS, self-serve kiosk, drive-thru, and an online storefront — all feed a single order engine that decomposes every order into station-level kitchen tickets, then posts the settled sale into finance and ingredient inventory automatically. Tills and the kitchen display keep serving through a power cut or dead link; a conflict-free sync engine reconciles the moment connectivity returns.

Channels

4-way ordering

Counter, kiosk, drive-thru and online — one pricing engine, computed server-side so a tampered client can't set its own price.

Kitchen

Station routing

Orders explode into fryer / grill / drinks / assembly tickets, sequenced by prep time so items in a basket finish together.

Money

Transaction-time FX

Every payment stores its captured USD⇄ZWG rate as exact decimals — reports stay economically true after any devaluation.

Intelligence

Grounded AI

Daypart demand forecasts drive prep-ahead, staffing and waste control — answered from the store's own numbers, with an evidence trail.

02 · Engineering contributions

Four things this system does that a generic POS doesn't

C1

Prep-time-aware kitchen routing

An order isn't one ticket — it's a set of station tasks (fryer, grill, drinks, assembly) with per-item prep durations. The router back-schedules each item so a bucket, fries and a drink land on the pass at the same moment, not three minutes apart.

Kitchen Display System
C2

Transaction-time multi-currency capture

Every monetary event persists (amount, currency, base_currency, exchange_rate, rate_source, captured_at) as NUMERIC(18,4). A sale rung at today's ZWG rate stays interpretable months later — reports convert with the captured rate, never today's.

Finance core
C3

Offline-first sync that can't lose a ticket

Orders and stock movements are immutable, client-UUID-keyed events (union-merge + dedupe = idempotent retries). Two offline tills selling the last combo are both accepted and flagged for review — never silently dropped, never double-counted.

Sync engine
C4

Grounded operational AI + digital twin

Forecasts, prep-ahead plans, staffing suggestions and food-cost anomaly detection run on lightweight, explainable models over the tenant's own figures. A discrete-event restaurant simulator stress-tests staffing and menu changes before they hit the floor.

Analytics / AI

05 · Data design

Recipe-linked, event-sourced core

Normalised to 3NF. Orders and stock movements are immutable ledgers so inventory and finance are reconstructable; every business-owned row carries a tenant_id under PostgreSQL row-level security.

CREATE TABLE order (
  id            UUID PRIMARY KEY,   -- client-generated
  tenant_id     UUID NOT NULL,
  shop_id       UUID NOT NULL,
  channel       TEXT NOT NULL,   -- counter|kiosk|drive_thru|online
  cashier_id    UUID,
  subtotal      NUMERIC(18,4) NOT NULL,
  tax_amount    NUMERIC(18,4) NOT NULL,
  total         NUMERIC(18,4) NOT NULL,
  currency      CHAR(3) NOT NULL,
  base_currency CHAR(3) NOT NULL,
  exchange_rate NUMERIC(18,6) NOT NULL,
  rate_source   TEXT NOT NULL,
  status        TEXT NOT NULL,   -- placed|cooking|ready|served|void
  captured_at   TIMESTAMPTZ NOT NULL
);

Design guarantees

Recipe-driven depletion

Committing an order line walks its recipe and writes exact StockMovement rows — food cost is derived, never guessed.

Immutable ledgers

order, stock_movement and journal_entry are append-only and event-sourced.

Tenant isolation

Row-level security on tenant_id is defence-in-depth beneath application RBAC.

08 · Intelligence layer

AI that runs the line, not just the dashboard

Lightweight, explainable models over the tenant's own figures — every recommendation ships with the evidence it was drawn from.

🔮 Daypart demand forecast

Per-item, per-15-minute forecasts with confidence bands feed the prep-ahead queue and the roster. Rolling-origin backtest reports MAPE / RMSE / MAE.

▲ lunch rush 12:00–13:30 · +40% wings

🍗 Prep-ahead & staffing

Converts the forecast into "drop 3 more chicken batches by 11:45" and "add a second fryer cook for the dinner peak" — safety-stock maths, not vibes.

⚑ understaffed 18:00–19:30 · +1 line cook

📉 Food-cost & waste anomalies

Flags food-cost % drift, deep-discount abuse, void frequency, oversell events and end-of-day waste outliers against each shop's own baseline.

✖ oil usage 2.3σ above baseline · shop #4

🧪 Digital-twin simulator

A discrete-event restaurant sim (the LAKA LAKA CHICKEN engine) stress-tests staffing, menu and pricing changes against a modelled rush before they hit the floor — service rate, wait time and profit per scenario.

✓ +2 fryers → service 34% → 83%

Grounded assistant: “Why was Shop 4 down last week?” → retrieves that tenant's sales, waste and roster, answers from them, and attaches the figures it used. Tenant-isolated at the retrieval boundary; no cross-store leakage.
